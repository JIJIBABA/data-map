数据地图——Java 项目数据血缘采集与可视化平台

---
第一章：项目概述
1.1 背景与问题域
1.1.1 企业系统演进中的数据迷雾
在企业级系统的长期迭代中，数据库表的数量持续增长，表与表之间的关联关系日益复杂。一个典型的企业级 Java 项目经过多年演进，可能包含数十甚至数百张业务表。这些表之间存在复杂的关联关系——外键、JOIN 查询、业务逻辑中的隐式依赖——但这些关系分散在代码的各个角落，难以形成全局视图。
这种"数据迷雾"带来多重挑战：
新人上手困难
当新加入的开发人员需要理解某个业务模块的数据模型时，通常需要：
- 翻阅实体类代码，了解表结构和字段定义
- 阅读 Mapper XML，理解表之间的 JOIN 关系
- 查看 Service 层代码，掌握字段的读写场景
- 请教老同事，获取口口相传的隐性知识
整个过程可能需要数天甚至数周，且严重依赖老员工的配合。一旦关键人员离职，大量隐性知识随之流失。

关联关系隐蔽
外键约束是物理层面的表关联，但在实际 Java 项目中：
- 很多项目根本不使用物理外键，关联完全在代码层维护
- MyBatis XML 中的 JOIN 关系隐藏在 SQL 语句中
- ResultMap 中的 association/collection 标签定义了对象嵌套关系
- Service 层的业务逻辑可能跨多个表操作
这些分散的关联信息需要串联起来，才能形成完整的表关系图。

字段使用场景不透明
当需要修改某个字段时，开发人员往往面临以下问题：
- 这个字段被哪些方法读取？
- 这个字段在哪些场景下被写入？
- 这个字段的数据来源是什么表？
- 这个字段被哪些 API 接口使用？
传统的代码搜索（grep/IDE Find Usages）虽然能找到字段引用，但无法区分读写场景，也难以追溯数据来源。

表间导航路径未知
当需要从表 A 关联查询到表 B 时，开发人员需要回答：是否存在连接路径？最短的连接路径是什么？通过哪些中间表？用哪些字段 JOIN？这些问题在缺乏全局关系图的场景下极难回答。

1.1.3 Data Map 的破局思路
Data Map 的核心洞察是：Java 项目的数据库元数据分散在三个层面，每个层面只提供一个维度的信息，但融合后可以还原完整的数据血缘关系。
具体而言：
- 实体类（Entity）：反映物理表结构和字段定义（@TableName、@TableId、@TableField 等注解）
- Mapper XML / 注解：反映表间的 JOIN 关联、ResultMap 的对象嵌套关系
- Service 层代码：反映字段的读写使用场景、方法级别的数据操作

将这三种信号统一采集、结构化存储，再通过图算法进行关联分析和路径计算，最终以交互式可视化界面呈现——这就是 Data Map 的核心思路。

1.2.2 解决的问题
问题一：表关联关系不可见
自动从代码中提取表间关联关系，以交互式关系图呈现。开发人员可以直观地看到某张表关联了哪些表、通过哪些字段连接、关系类型是什么。

问题二：表间查询路径未知
通过 BFS 图搜索算法，自动发现任意两张表之间的连接路径，返回最短路径及每一步的 JOIN 字段对。最大深度 6 跳，最多返回 10 条路径。

问题三：字段使用场景不清晰
记录每个字段在哪些方法中被读取、写入或更新，每个使用场景的数据来源表和来源 API，形成完整的字段使用画像。

问题四：人工标注被自动扫描覆盖
引入手动标注保护机制（tableCommentManual / fieldCommentManual 标志位），重新扫描时自动跳过人工编辑过的注释内容。

1.3 设计哲学
1.3.1 扫描与展示分离
核心原则：扫描器和展示平台是两个独立运行的组件。

Data Map 采用 推式架构（Push Architecture）：
- 扫描器（CLI 工具）负责分析 Java 源码，产出标准化的 JSON 数据
- 后端 API 负责接收 JSON 数据，进行结构化存储
- 前端负责可视化展示和交互查询

这种设计的好处：
- 扫描器和展示平台可以独立演进、独立部署
- 扫描结果可以跨项目复用
- API 契约（ScanResultDTO）成为两个组件的清晰边界

1.3.2 关联关系双向化
核心原则：存储时保留方向性，查询时视为无向边。

表关联关系在数据库中以有向边存储（sourceTableId → targetTableId），但图查询（关系图展开、路径搜索）均视为无向边处理。这种设计兼顾了：
- 存储的语义准确性（保留关系的原始方向信息）
- 查询的实用性（关联图可以双向扩展，表间路径可以双向遍历）

1.3.3 人机协作，手动优先
核心原则：自动扫描提供基础数据，人工标注拥有最终决定权。

Data Map 认识到自动扫描无法 100% 准确提取业务语义：
- 字段注释可能不准确或缺失
- 表注释可能过于技术化，缺乏业务含义
- 关联关系类型可能需要人工校正

因此系统区分自动扫描和人工编辑两种状态，重新扫描时只覆盖未被人工编辑过的内容。

1.3.4 渐进式交付
核心原则：先看见全貌，再深入细节。

交互流程设计遵循渐进式原则：
1. 项目列表 → 选择项目，看到该项目的所有表
2. 表详情 → 点击某张表，展开看到所有字段
3. 字段使用场景 → 展开某个字段，看到该字段的读写场景
4. 关联关系图 → 从表详情跳转到关系图，看到该表在整个关系网络中的位置
5. 路径查询 → 选择起止表，找到连接路径

每一步都是上一步的自然深入，降低新用户的认知负荷。

1.4.2 分层设计

扫描层（Scanner Layer）
- 职责：解析 Java 项目源码，提取结构化元数据
- 输入：Java 项目根目录
- 输出：标准化 JSON（ScanResultDTO 格式）
- 技术：Java 源码分析（识别注解、XML 解析、代码模式匹配）

传输层（Transport Layer）
- 职责：将扫描结果安全提交到后端
- 协议：HTTP POST /api/scan/result
- 格式：JSON（ScanResultDTO 契约）

持久化层（Persistence Layer）
- 职责：结构化存储元数据，保护人工标注
- 技术：MySQL + MyBatis-Plus
- 设计：6 张核心表，全部支持逻辑删除和手动标注保护

查询层（Query Layer）
- 职责：提供关系图展开、路径搜索、字段搜索等查询能力
- 算法：DFS 递归展开（关系图）、BFS 双向搜索（路径查询）
- 输出：VO 对象，前端直接渲染

展示层（Presentation Layer）
- 职责：交互式可视化数据地图
- 技术：React 18 + Ant Design 5 + @xyflow/react + dagre
- 核心页面：表管理、表详情、关联图、逻辑查询

1.6 适用场景与限制
1.6.1 适用场景

场景一：遗留系统接手
当新团队接手一个开发多年的 Java 项目时，Data Map 可以快速生成完整的数据模型地图。从表管理页面可以浏览全部数据表，从关系图可以看到表间关联的全貌，从路径查询可以找到任意两表的 JOIN 路径。

场景二：代码评审中的数据影响分析
在代码评审中，当某张表的字段发生变更时，可以通过字段使用场景追溯受影响的方法和 API，评估变更的潜在影响范围。

场景三：跨表查询辅助
当需要编写涉及多表关联的复杂查询时，可以通过路径查询功能快速找到两表之间的 JOIN 路径及其字段映射，避免在大量 Mapper XML 中手动搜索。

场景四：技术文档自动化
在项目交接或技术文档编写时，Data Map 提供结构化的数据模型视图，可直接截图或导出作为数据架构文档的一部分。

第二章：数据采集层设计
2.1 设计考量
2.1.1 为什么需要多源采集
在 Java 项目中，数据库表的"业务含义"并非仅由实体类决定。同一张表在实体类中定义结构，在 Mapper XML 中定义关联，在 Service 中定义使用场景——只有从这三个层面综合采集，才能构建完整的数据血缘视图。

三个采集源的分工：

数据源
采集内容
在数据地图中的作用
实体类（Entity）
@TableName 表名、字段名、字段类型、主键标识、字段注释
构建表结构和字段列表
Mapper XML
SQL 中的 JOIN 关系、ResultMap 中的 association/collection 嵌套
构建表间关联关系
Service 代码
方法名、操作类型（读/写/更新）、业务场景描述
构建字段使用场景

多源融合的价值示例：
假设有以下代码：

```java
// 实体类
@TableName("tb_order")
public class Order {
    @TableId("order_id")
    private Long orderId;
    private Long userId;
    private String orderStatus;
}

// Mapper XML
<resultMap id="orderWithUser" type="Order">
    <association property="user" javaType="User">
        <id property="userId" column="user_id"/>
    </association>
</resultMap>

// Service
public void cancelOrder(Long orderId) {
    // 取消订单时更新订单状态字段
    Order order = orderMapper.selectOrderWithUser(orderId);
    orderMapper.cancelOrder(orderId);
}
```

仅从实体类，我们只能知道 tb_order 表有 order_id、user_id、orderStatus 三个字段。
结合 Mapper XML，我们进一步知道 tb_order 与 tb_user 通过 user_id 关联。
结合 Service 代码，我们还知道 cancelOrder 方法读取了 orderStatus 字段（通过 selectOrderWithUser），写入了 orderStatus 字段（通过 cancelOrder）。

结论：单一数据源只能揭示数据模型的一个侧面，只有多源融合，才能完整还原数据血缘。

2.1.2 推式采集架构
Data Map 采用推式架构（Push Architecture），而非拉式架构（Pull Architecture）。

推式架构的工作流程：
1. 扫描器 CLI 工具分析 Java 项目源码
2. 生成符合 ScanResultDTO 契约的 JSON 数据
3. 通过 POST /api/scan/result 提交到后端
4. 后端 ScanService 进行 upsert 操作

推式架构的优势：
- 解耦：扫描器的技术栈可以与后端完全独立
- 离线：扫描在本地执行，不依赖后端运行状态
- 可批量：一次扫描提交完整结果，减少网络开销
- 可审计：扫描记录（ScanRecord）提供完整的操作审计

2.2.2 字段注释提取

2.3.2 INSERT/UPDATE/DELETE 语句的字段识别

从 UPDATE 语句提取：orderStatus 被 UPDATE 操作，order_id 被 READ 操作（在 WHERE 子句中）。

2.4 Service 层分析
2.4.1 字段使用场景提取
Service 层代码揭示了最高层次的字段使用意图。扫描器通过分析方法调用和上下文来推断字段使用场景：

```java
public void createOrder(Order order, List<OrderItem> items) {
    orderMapper.insertOrder(order);      // WRITE: tb_order 所有字段
    for (OrderItem item : items) {
        orderMapper.insertOrderItem(item); // WRITE: tb_order_item 所有字段
    }
}
```

使用场景的提取规则：
- 调用 insert* → 对应表的所有字段标记为 WRITE
- 调用 update* → SET 子句字段标记为 UPDATE，WHERE 子句字段标记为 READ
- 调用 select* → SELECT 列和 WHERE 条件字段标记为 READ
- 调用 delete* → WHERE 条件字段标记为 READ（定位要删除的记录）

第三章：关联图与路径查询引擎
3.1 问题定义
3.1.1 什么是「关联关系图」
关联关系图是以数据库表为节点、以表间关联关系为边的无向图（或双向有向图）。图中的每条边代表两张表之间存在业务或物理上的关联，边上标注了关联字段和关联类型。

关联关系图示例：
```
 tb_user ──────── tb_order ──────── tb_order_item
           user_id       order_id
         = user_id     = order_id
```

在这个图中：
- tb_user 与 tb_order 通过 user_id 关联（1:N，一个用户多个订单）
- tb_order 与 tb_order_item 通过 order_id 关联（1:N，一个订单多个明细项）

3.1.2 什么是「表间路径」
表间路径是指在关联关系图中，从起始表到目标表所经过的一系列边和中间节点。每条路径显式给出了每一步的 JOIN 字段对。

例如，从 tb_user 到 tb_order_item 的路径：
```
tb_user → tb_order → tb_order_item
  user_id      order_id
= user_id    = order_id
```

这条路径告诉开发者：要关联查询用户和他的订单明细，需要先 JOIN tb_order 通过 user_id，再 JOIN tb_order_item 通过 order_id。

3.2 关系图展开算法
3.2.1 DFS 递归展开
当用户查看某张表的关系图时，系统需要找到与该表相关的所有表（连通分量）。

RelationService.getRelations(tableId) 实现了 DFS 递归展开：

```
算法：连通分量发现
输入：起始表 ID
输出：连通分量中的所有表节点和关联边

1. 初始化结果集 result = {startId}
2. 从 startId 开始递归：
   a. 查询所有 source = id 或 target = id 的 relation
   b. 对每条 relation：
      - 确定邻居节点（source side → 取 target，target side → 取 source）
      - 将邻居加入 result
      - 递归处理邻居
3. 收集 result 中所有表的信息和它们之间的 relation
4. 返回 nodes + edges + details
```

复杂度分析：
- 时间复杂度：O(N + E)，其中 N 为连通分量中的表数，E 为边数
- 空间复杂度：O(N)，递归深度最多为连通分量的直径
- 实际表现：百级表规模下 < 1s 完成

3.2.2 双向遍历设计
虽然 relation 在数据库中单向存储（sourceTableId → targetTableId），但在图查询时视为无向边：

```java
// 递归核心逻辑
for (TableRelation r : relations) {
    Long next = r.getSourceTableId().equals(id)
        ? r.getTargetTableId()  // 当前表是 source，取 target
        : r.getSourceTableId(); // 当前表是 target，取 source
    result.add(next);
    collectAll(next, result, visited);
}
```

这个设计确保了关系图可以双向展开，无论数据录入时选择了哪个方向作为 source。

3.3 路径搜索算法
3.3.1 BFS 最短路径优先
QueryService.findPath() 使用 BFS（广度优先搜索）确保先找到的路径一定是最短路径。

```
算法：BFS 最短路径搜索
输入：projectId, startTableId, targetTableId
输出：最多 10 条路径，按长度升序排列

1. 加载该项目所有 relation，构建双向邻接表
2. 初始化队列，将起始表的所有出边作为初始路径
3. BFS 循环：
   a. 出队一条路径
   b. 如果路径长度 > 6，跳过
   c. 如果路径终点 = 目标表，记录路径
   d. 否则，沿邻接边扩展新路径并入队
   e. 已访问节点集合去重（目标表除外）
4. 对找到的路径按长度排序后返回
```

5.2 存储设计决策
5.2.1 逻辑删除与物理删除
所有核心表均使用 status 字段实现逻辑删除：
- status = 1：有效记录
- status ≠ 1：已删除记录

逻辑删除的优势：
- 数据可恢复，避免误删
- 保留历史数据，便于审计
- 删除操作不触发级联删除，而是通过查询条件过滤

5.2.2 手动标注保护字段
table_info 和 table_field 表中均设有 _manual 标志位：

```
table_comment_manual: 0 = 自动, 1 = 人工
field_comment_manual: 0 = 自动, 1 = 人工
```

在 ScanService.upsertTableAndFields() 中：
- 新记录：comment 直接写入，_manual 设为 0
- 已有记录且 _manual != 1：覆盖 comment
- 已有记录且 _manual == 1：跳过 comment 覆盖

这个机制确保了重新扫描不会覆盖人工优化过的业务注释。

5.2.3 table_id 冗余
field_usage_scenario 表中同时存储 field_id 和 table_id，这是一种受控的冗余：
- table_id 方便直接从表维度查询所有字段的使用场景（无需 JOIN table_field）
- 维护成本极低（场景创建时，table_id 已确定）

5.3 自动化字段填充
MyBatis-Plus 的 MetaObjectHandler 提供了字段自动填充能力：
- 插入时自动填充：status = 1, createdAt = now(), updatedAt = now()
- 更新时自动填充：updatedAt = now()

这避免了在每个 Service 方法中手动设置时间戳和状态字段，减少了遗漏的风险。
